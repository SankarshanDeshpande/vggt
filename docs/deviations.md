# Deviations from VGGT Paper / Official Setup

Every deviation is listed here, in the corresponding code comments, and in the results table.
No silent substitutions.

| # | Paper / official spec | What was actually done | Reason | Effect on results |
|---|---|---|---|---|
| 1 | Trained on ~16 datasets (Co3Dv2, BlendMVS, DL3DV, MegaDepth, Kubric, WildRGB, ScanNet, HyperSim, Mapillary, Habitat, Replica, MVS-Synth, PointOdyssey, VKitti, Aria×2, Objaverse-like) | Fine-tuned on **CO3Dv2 (`apple` category) only** | Only dataset (besides VKitti) with a ready-made `Dataset` class in the officially released training code; others would need a new loader written from scratch | Training run validates pipeline correctness only, not paper-scale generalisation |
| 2 | CO3D full category (~100GB, ~700+ sequences for `apple`) | CO3D **single-sequence subset** (3 sequences, 202 frames each) | Full download blocked by compute-node network access; single-sequence subset small enough to transfer via `scp` from a local PC | Training/val statistics are on 3 sequences only — not a meaningful train/test split, smoke-test scale |
| 3 | Train/val split as defined by CO3D | Both train and val configs point at CO3D **`split: test`** | The single-sequence subset's 3 sequences happen to belong to CO3D's test split; `split: train` produced an empty dataset for this subset | Reported train/val losses are not a genuine train/val split — train and val draw from the same 2–3 sequences |
| 4 | `debug: False`, all 40+ SEEN_CATEGORIES loaded | `debug: True` (restricts `Co3dDataset` to `apple` category only) | Only `apple` category data exists on disk locally | Matches available data; not representative of full-category training |
| 5 | `limit_train_batches: 800`, `limit_val_batches: 400`, `max_epochs: 20` | `limit_train_batches: 10`, `limit_val_batches: 5`, `max_epochs: 1` | Dataset scale (3 sequences) does not support the default batch/epoch budget; this run's purpose was pipeline validation, not a trained model | One 10-batch epoch — loss values shown are a pipeline sanity check, not a converged/trained result |
| 6 | Multi-GPU training via `torchrun --nproc_per_node=N` (paper: 64× A100, 9 days) | Single H100 (fractional `shard` allocation), `--nproc_per_node=1`; later run **in-process inside the Jupyter kernel** (bypassing `torchrun`/DDP launch) rather than as a separate subprocess | Available hardware is a single shared H100 per allocation, not a multi-GPU cluster; subprocess/torchrun launches were being killed by an (eventually identified) SSH-tunnel instability, whereas in-kernel execution on an already-stable session was not | No distributed-training behaviour exercised; DDP code path present in config but effectively single-process |
| 7 | Custom-loaded VGGT-1B checkpoint via `torch.hub.load_state_dict_from_url` (HF Hub) | Checkpoint manually downloaded on local PC, transferred via `scp`, loaded via `torch.load(..., map_location="cpu")` with `strict=False` | `huggingface.co` unreachable from compute nodes | `strict=False` silently accepts extra keys (`point_head.*`, `track_head.*` from the full checkpoint) since this fine-tune only enables camera + depth heads — confirmed these are the *only* mismatched keys, not a sign of a corrupted/wrong checkpoint |
| 8 | Point/track heads part of the full model | `enable_point: False`, `enable_track: False` in model config (repo default for CO3D fine-tuning) | Matches the repo's own documented default config for this fine-tuning setup, not changed by us | Point-map and tracking outputs untested in this fine-tune |
| 9 | Paper's qualitative Figure 3 examples (oil painting, no-overlap pair, repeated-texture scene) — no dataset named in the paper text | Used the VGGT repo's bundled `examples/single_oil_painting` and `examples/room` (no_overlap set) folders as the closest available match, plus `examples/videos/pyramid.mp4` for an additional out-of-domain test | Paper explicitly does not name a source dataset for these figures (confirmed by reading the published text); repo's own bundled demo assets are the most legitimate stand-in | Cannot claim pixel-identical reproduction of the paper's exact figure inputs, only the same category of qualitative test |
| 10 | Confidence filtering — paper's own demo default `conf_thres_value = 5.0` (absolute) | Initially used `np.percentile(conf, 50)` (a **relative** threshold, always keeps bottom 50% regardless of quality) before catching the error; corrected to the absolute `5.0` (loosened to `3.0`/`1.5` for sparser scenes) | Percentile approach was a mistake, not a deliberate choice — corrected once identified | Early exploratory point-cloud renders (before the fix) retained more background noise than intended; all final renders use the absolute threshold |
| 11 | — (not in paper) | Added k-NN statistical outlier removal (`scipy.spatial.cKDTree`) before visualisation | Engineering addition to clean floating-fragment noise for visualisation clarity, not part of VGGT's own output | Purely a display-time filter; does not affect the underlying model predictions or the exported point-count-complete `.ply` unless explicitly applied before export |
| 12 | Standard visualisation (paper likely uses `viser`, per repo's `demo_viser.py`) | Custom NumPy z-buffer renderer (`matplotlib`-based scatter initially, replaced due to lack of depth-sorting) | `viser`/real-time GPU point renderer not set up in this environment; matplotlib alone is insufficient for correct occlusion, so a manual z-buffer was written | Visual quality (anti-aliasing, splat softness) is lower than the paper's renderer even with correct geometry; `.ply` export is provided as the renderer-independent artifact |
| 13 | Video input handled by fixed-rate/native frame extraction (implementation detail not specified) | 32 (later up to 96) evenly-spaced frames sampled by decoding the full video sequentially and indexing into the true decoded-frame list, not `cv2.set(CAP_PROP_POS_FRAMES)` seeking | `cv2` seek-based extraction was unreliable (returned fewer frames than requested) due to inaccurate container frame-count metadata / keyframe-only seeking on this video codec | None on final results; documented because it cost significant debugging time and is a reusable gotcha |
| 14 | Room-scale training data: ScanNet / Replica / HyperSim / Habitat (paper) | **Not yet trained on** — currently only used VGGT zero-shot (no fine-tuning) for room-scale qualitative tests (`kitchen`, `room`), and Replica download in progress for future work | Room-scale dataset classes not present in released training code; requires custom `Dataset` implementation, planned but not yet built | Room-scale results in this document are inference-only, using the CO3D-apple-fine-tuned (or base) checkpoint, not a room-fine-tuned model |

## Open questions not yet resolved

- Whether to fine-tune on Replica once the room-scale `Dataset` class is written, or continue using
  VGGT zero-shot for the ConceptGraphs-facing pipeline (paper reports strong zero-shot generalisation;
  worth testing before committing to a room-specific fine-tune — noted as of Phase D).
- Metric scale accuracy of VGGT-predicted depth/pose vs Replica ground truth has not yet been
  quantitatively measured — planned as the Phase 2 experiment (Replica RGB → VGGT vs Replica GT depth,
  same ConceptGraphs downstream stage, compare scene-graph quality).
